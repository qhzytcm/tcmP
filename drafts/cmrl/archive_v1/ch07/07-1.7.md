## [Part2] 7.7 平台实践与实训：tcmP 平台的在线策略优化

### 7.7.1 平台语境：对话即进化信号

tcmP 中医药智能平台以六者 Agent（医者/患者/药者/械者/规者/法者）构成中医药服务的完整闭环：医者 Agent 负责辨证与推荐，药者 Agent 负责审方把关，规者 Agent 负责质控评估，患者 Agent 模拟就医行为，械者 Agent 对接智能设备，法者 Agent 提供合规约束。在这个平台上，Q-learning 与平台的在线进化机制高度吻合。平台的六者 Agent 每天都在与用户对话，每次对话都是一次策略更新的机会：状态 = 患者症状 + 上下文（主诉、既往史、user_level 等），动作 = 推荐的辨证结论与方剂，奖励 = 用户反馈（采纳、复诊转归、药者审方结果）。平台的"对话 = 进化信号"闭环，正是 Q-learning 的分布式实现：每次对话更新 $Q(\text{症状}, \text{动作})$ 表中的对应条目，无数个 Agent 实例的对话汇聚成一张不断进化的策略表。平台的"医圣成长路径"——从静态知识库（医圣 SOUL 人格 + 病证单元库）起步，通过真实对话持续进化——正是"初始化为先验知识、在线更新为经验学习"的强化学习范式在中医药场景中的具象化。

奖励信号的设计是平台实践的第一课，它直接对应本章的数学结构。药者审方拒绝（reject）是天然的负奖励：当医者推荐与患者情况冲突的方剂（如十八反、配伍禁忌）时，审方拒绝产生一个大的 TD 误差，驱动医者策略调整——下次遇到同类症状组合时该动作的价值被压低。药者审方通过（accept）则是正奖励，用户采纳与复诊好转提供更强的长期回报信号。除审方结果外，平台还提供两个奖励源：其一是语义检索的证据分（rrf 分数），它是"推荐与知识库证据的相似度"的连续值度量，可作为连续奖励；其二是规者 Agent 的质控指标（处方合规率、床位周转率等），构成"证据等级"维度的补充信号。与教科书中的单值奖励不同，平台实际面临的是多维奖励，实践中需要加权合成：$r = w_1 \times \text{证据分} + w_2 \times \text{审方结果} + w_3 \times \text{转归}$，权重的选取本身就是策略的一部分。平台六者之间"医者推荐 → 药者审核 → 规者质控"的链路，正是强化学习中"智能体行动、环境评判、监督者纠偏"的现实投影——每个 Agent 都是学习者，审核链就是教师。

### 7.7.2 平台接口：交互数据与奖励信号

把理论落到代码，首先需要熟悉平台的四个数据接口。其一，交互数据源：/consult/sage-zhang-zhongjing 的问答日志，字段包含 user_level（用户层级）、主诉（症状文本）、回复内容（辨证结论与方剂）——这份日志是天然的 $(s, a)$ 数据对来源，即"状态-动作"序列。其二，奖励信号接口：/semantic-search 语义检索接口返回 rrf 证据分（连续值奖励，范围通常映射到 [0,1]），/pharmacists/review 处方审核接口返回 reject/accept（离散奖励，可取 +1/−1）。其三，实现依赖：numpy 即可——Q 表就是一个"状态数 × 动作数"的矩阵，无需 gym 等强化学习库，平台 API 本身就是环境。其四，线上入口：/agents/{role}/chat 是六者 Agent 的交互端点，实验中的"环境"可以封装为对这四个接口的调用组合。一个最小可用的环境封装建议如下：定义 PlatformEnv 类，提供 step(s, a) 方法，内部依次调用审方接口与检索接口，合成奖励并返回后继状态 $s'$——后继状态可以由真实对话流驱动（用户回复构成下一状态），也可以在教学切片中由预定义转移规则驱动。

奖励的工程化处理有三个要点。第一，归一化：rrf 证据分的分布随查询而变化，建议按批次做 min-max 归一化，使其落在 [0,1]，否则不同查询之间的奖励尺度不一致会干扰学习率的选择。第二，负奖励的不对称性：审方 reject 的惩罚权重应高于普通正奖励——推荐一个被拒方剂的代价不仅是"失去一次采纳"，还包含患者信任损失与合规风险，因此实践中常取 reject = −1、accept = +0.2 的不对称设计，或干脆把审方结果作为硬约束（reject 时该 (s,a) 的 Q 值直接设为极小值）。第三，多信号合成：检索证据分是"知识相似度"，审方结果是"安全性"，转归是"疗效"，三者合成为奖励时应有明确语义——如果实验目标是"复现检索最优"，则证据分权重占主导；如果目标是"安全优先"，则审方结果应设为硬约束。这些细节在教科书例题中不会出现，却是平台实践决定成败的工程常识。环境封装的好处在于：学习器只与 PlatformEnv 交互，算法代码与第7章教材中的通用实现完全一致，平台 API 的细节全部藏在环境内部——这保持了"算法与平台解耦"的清晰架构。

### 7.7.3 本章实践：mini Q-learning 复现检索最优

本节实践任务的目标是：用 mini Q-learning 复现"检索式推荐的最优结果"，从而把本章的核心算法与平台真实检索信号对接，体会"对话日志 = 训练数据"这一平台进化机制。任务设计如下。第一，状态空间：3 类症状组合——失眠（入睡困难、多梦、心悸）、感冒（恶寒发热、头身痛、脉浮）、头痛（头痛、项强、脉弦），每类取一组典型主诉文本作为状态标识。第二，动作空间：每类症状 2 首候选方剂，例如失眠候选 {酸枣仁汤, 天王补心丹}，感冒候选 {荆防败毒散, 银翘散}，头痛候选 {川芎茶调散, 天麻钩饮}。第三，奖励：检索证据分——通过 /semantic-search 实查（症状文本查询方剂文本）或本地 tcm_embed 计算余弦相似度并映射到 [0,1]。第四，探索：ε-贪婪，ε 从 0.5 线性衰减到 0.05。第五，训练：100 轮（episode），每轮从某个症状状态出发，与"环境"交互若干步——推荐方剂 → 药者审方 → （模拟或真实）复诊转归 → 更新 Q 表。训练结束后观察：Q 表是否收敛到与平台检索 Top1 对应的动作？

围绕实验结果，有三组观察问题值得深入思考。其一，ε 与收敛速度的关系：ε 大则探索充分、可能发现更多候选，但收敛慢；ε 衰减过快则可能过早锁定次优方剂（未探索到证据分更高的动作）。建议同时运行"ε 固定 0.1""ε 固定 0.5""ε 从 0.5 衰减到 0.05"三组，对比收敛曲线与最终一致率。其二，Q-learning 能否"复现"检索式推荐的最优结果：若检索证据分与真实疗效高度相关，Q 表应收敛到检索 Top1 对应的动作；若不一致，说明检索分与长期疗效之间存在偏差——而这恰恰是强化学习相对静态检索的价值所在：Q-learning 优化的是"长期价值"（含复诊转归与审方反馈的累积回报），而非单点相似度。其三，负奖励如何改变 Q 表：被审方拒绝的方剂，其 Q 值应显著下降并在后续推荐中被回避——这是"药者审方 = 负奖励"的最直接证据。进阶思考：把"对话日志 = 训练数据"落成脚本，定期离线重放历史日志批量更新 Q 表（正是 7.6.2 节批量 TD 思想的工程化），就得到平台 CI/CD 进化闭环的算法原型——每日日志 → 离线批量更新 → 评估 → 上线。实训的具体操作步骤、代码骨架与常见错误，见 7.7.4 至 7.7.6 节。
