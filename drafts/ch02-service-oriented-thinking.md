## 2.1 情境导入：Hermes Delivery 的成长烦恼

小陈是 Hermes Delivery 的初创工程师。三个月前，他和两位同事用 Go 语言写了一个单体应用——订单管理、骑手调度、运费计算、用户通知全塞在一个代码仓库里，部署就是一台云服务器加一个 MySQL 实例。

起初一切顺利。但最近，团队从 3 人扩到 15 人，业务也多了起来：新增了"同城急送"和"跨城专送"两条产品线，接入了微信支付和支付宝双通道，运营团队还要求实时查看配送热力图。

问题像多米诺骨牌一样倒下：

- **周一**：小陈改运费计算逻辑，不小心改了订单表的结构，导致骑手调度模块集体报错。两个功能看似无关，却共享同一张数据库表。
- **周三**：运营想加一个"配送超时预警"功能，但发现需要读懂骑手调度、订单流转、GPS 上报三个模块的代码才知道该在哪里插逻辑。没人能说清整个系统的"业务边界"在哪。
- **周五**：产品经理想把"用户评价"功能拆给新来的实习生独立开发。但评价模块的代码和订单模块纠缠在一起——拆不出来。

这几乎是每个从单体起步的系统都会遭遇的问题：**代码边界模糊、业务逻辑耦合、团队协作冲突**。根源不在于技术选型，而在于——**我们从未认真定义过"什么是服务的边界"**。

本章要回答的核心问题就是：**如何从业务需求出发，科学地划分服务的边界？**

## 2.2 领域驱动设计（DDD）入门

### 2.2.1 为什么需要 DDD？

传统的软件设计方法往往以"技术分层"为起点——先画 Controller → Service → Repository 三层架构，然后把需求往里塞。这在业务逻辑简单时效率很高，但面对 Hermes Delivery 这样多产品线、多角色的复杂业务时，技术分层无法回答一个根本问题：

> **"这一行代码，到底属于哪个业务？"**

领域驱动设计（Domain-Driven Design，DDD）的核心理念是：**让软件模型忠实地反映业务领域的结构**。它不教你怎么写代码，而是教你**怎么理解业务、怎么划分边界**。

打个比方：如果软件架构是一座城市，技术分层只是规定了每栋楼有几层（管线层、居住层、商业层），而 DDD 告诉你**城市应该划分成哪些街区，每个街区承担什么职能**。

### 2.2.2 战略设计与战术设计

DDD 分为两个层面：

| 层面 | 关注点 | 核心概念 | 类比 |
|------|--------|---------|------|
| **战略设计** | "大的结构"——业务如何切分 | 限界上下文、上下文映射、子域 | 城市规划：划分功能区 |
| **战术设计** | "小的构造"——单个上下文内部如何组织 | 实体、值对象、聚合、领域服务 | 建筑设计：单栋楼的内部布局 |

本章聚焦于**战略设计**——因为对于服务化架构来说，边界的划分远比边界内部的实现细节重要。一个上下文内部写得再优雅，如果上下文本身划分错了，整个系统仍然是一团乱麻。

### 2.2.3 统一语言（Ubiquitous Language）

在 Hermes Delivery 的早期，小陈发现一个令人头疼的现象：

- 产品和运营说的"订单"，指的是用户下单到签收的整个流程；
- 财务说的"订单"，只关心支付金额和结算状态；
- 骑手端说的"订单"，实际上是一条待配送的任务。

同一个词，三个含义。代码里自然也就出现了各种 `order.status`、`order.payment_status`、`task.status` 混用的场景。

DDD 提出**统一语言**（Ubiquitous Language）的概念：**在每个限界上下文内部，所有参与者——开发人员、产品经理、领域专家——使用同一套术语，且这些术语直接映射到代码中的类名、方法名和变量名**。

统一语言不是全公司用一套词典，而是**一个上下文一套语言**。在"订单上下文"里，"订单"就是订单；在"配送上下文"里，那就是"运单"或"任务"。关键不是统一词汇本身，而是明确词汇的**上下文归属**。

## 2.3 限界上下文（Bounded Context）

### 2.3.1 什么是限界上下文？

限界上下文（Bounded Context）是 DDD 中最核心的概念。我们先用一个生活类比来建立直觉：

> 你去医院看病。挂号处说的"病人"指的是一个挂号记录（姓名、年龄、科室）；诊室里医生说的"病人"指的是一个临床对象（症状、病史、诊断）；收费处说的"病人"指的是一个结算主体（医保类型、待缴费用）。同一个人，在不同"上下文"里有不同的含义。

在软件系统中，**限界上下文就是一个语义边界**：在这个边界之内，所有术语都有明确、一致的含义；跨出这个边界，同一个词可能意味着完全不同的东西。

限界上下文通常具有以下特征：
- **内聚性**：上下文内部的业务逻辑高度相关
- **自治性**：每个上下文可以独立演进、独立部署
- **明确的接口**：上下文之间通过定义良好的接口（API、事件）通信，而非共享数据库

### 2.3.2 上下文映射（Context Map）

识别出限界上下文后，下一步是理清它们之间的关系。DDD 用**上下文映射**（Context Map）来描述上下文之间的协作模式：

| 关系模式 | 含义 | 例子 |
|---------|------|------|
| **共享内核**（Shared Kernel） | 两个上下文共享一部分模型，需要高度协作 | 订单上下文和支付上下文共享"金额"和"币种"的定义 |
| **客户-供应商**（Customer-Supplier） | 上游（供应商）提供能力，下游（客户）消费能力；下游可以提需求但不能控制上游 | 配送上下文（供应商）向订单上下文（客户）提供配送状态 |
| **防腐层**（Anti-Corruption Layer, ACL） | 下游通过一个翻译层隔离上游模型的变化 | 用户上下文对接外部微信用户系统时，加一个 ACL 把微信的 OpenID 映射为内部的 UserID |
| **开放主机服务**（Open Host Service, OHS） | 上游提供一套标准 API 供所有下游调用 | 通知上下文提供统一的 `/notify` 接口 |
| **发布语言**（Published Language） | 配合 OHS 使用，定义标准化的消息格式 | 所有上下文间传递的事件使用 JSON Schema 约束的格式 |
| **各行其道**（Separate Ways） | 两个上下文没有集成关系，各自独立发展 | 内部报表上下文和实时调度上下文各走各路 |

### 2.3.3 Hermes Delivery 的限界上下文初探

回到 Hermes Delivery，我们可以从业务需求出发，初步识别出以下限界上下文：

```
┌──────────────┐     ┌──────────────┐     ┌──────────────┐
│   用户上下文   │     │   订单上下文   │     │   支付上下文   │
│  (User)       │────→│  (Order)      │────→│  (Payment)    │
│  注册·登录     │     │  下单·查询·取消 │     │  收款·退款·对账 │
│  地址管理      │     │  状态流转      │     │              │
└──────┬───────┘     └──────┬───────┘     └──────────────┘
       │                    │
       │            ┌───────┴───────┐
       │            │   配送上下文   │
       │            │  (Dispatch)   │
       │            │  接单·取件·送达 │
       │            │  路线规划      │
       │            └───────┬───────┘
       │                    │
┌──────┴───────┐    ┌──────┴───────┐
│   账户上下文   │    │   通知上下文   │
│  (Account)    │    │  (Notification)│
│  余额·账单    │    │  短信·推送·邮件 │
└──────────────┘    └──────────────┘
```

每个上下文内部拥有自己的数据模型。例如，"用户上下文"中的 `User` 包含昵称、手机号、默认地址；而"账户上下文"中的 `Account` 包含余额、优惠券列表。它们可能指向同一个人，但承载的信息维度完全不同。

## 2.4 服务拆分策略

识别出限界上下文只是第一步。下一步是决定：**哪些上下文应该成为独立的服务（微服务）？哪些可以合并？**

### 2.4.1 策略一：按业务能力拆分

**按业务能力**（Business Capability）拆分是最直观的策略。一个业务能力就是一个组织"做什么"的单位——它通常对应一个业务部门或团队。

以 Hermes Delivery 为例，业务能力拆分为：

- **用户管理能力** — 用户注册、登录、实名认证
- **订单管理能力** — 创建订单、查询订单、取消订单
- **运力调度能力** — 匹配骑手、规划路线、监控配送进度
- **计价计费能力** — 计算运费、优惠券抵扣、生成账单
- **支付结算能力** — 对接支付渠道、处理退款、与骑手结算
- **通知触达能力** — 短信、推送、邮件、站内信

按业务能力拆分有一个显著优点：**与组织结构天然对齐**。用户团队负责用户服务，调度团队负责调度服务——谁开发、谁运维一目了然。

但它也有局限：业务能力是"组织当前怎么做事"的镜像。如果组织架构不合理呢？这就引出了第二种策略。

### 2.4.2 策略二：按子域拆分

DDD 将业务领域划分为三类子域：

| 子域类型 | 含义 | 特征 | Hermes Delivery 实例 |
|---------|------|------|---------------------|
| **核心域**（Core Domain） | 让你区别于竞争对手的能力 | 需要最优秀的人才，值得最大的投入 | 运力调度——路径规划算法、动态定价模型是 Hermes 的核心壁垒 |
| **支撑域**（Supporting Domain） | 支撑核心业务运转，但不构成差异化优势 | 可以定制开发，也可以用现成方案 | 订单管理、用户管理——每家公司都有，但需要按自己流程定制 |
| **通用域**（Generic Domain） | 通用能力，没有行业特殊性 | 优先采购现成方案，除非有特殊需求 | 支付（用微信/支付宝 SDK）、通知（用云服务商短信平台）、身份认证（用 OAuth 标准方案） |

按子域拆分的策略是：**核心域自己造、支撑域定制化、通用域买现成**。

> 💡 **核心洞察**：对核心域的投资应该"过度"，对通用域的投资应该"吝啬"。小陈如果把 80% 精力花在自建支付系统和自研短信网关，却用最简单的贪心算法做骑手调度——那就本末倒置了。

### 2.4.3 两种策略的对比与组合

| 维度 | 按业务能力 | 按子域 |
|------|----------|--------|
| 拆分依据 | 组织做什么 | 对业务的价值 |
| 粒度 | 相对固定 | 可粗可细 |
| 优势 | 与团队边界一致 | 指导资源分配优先级 |
| 风险 | 固化不合理组织 | 核心域过于碎片化 |

实际操作中，两者可以结合使用：

1. **先用子域分析确定优先级**——识别出核心域、支撑域、通用域，决定投资策略
2. **再用业务能力确定边界**——将核心域和支撑域拆分为具体的业务能力，映射到开发团队

## 2.5 康威定律

### 2.5.1 原始定律

1967 年，计算机科学家梅尔文·康威（Melvin Conway）提出了一条著名的论断：

> **"任何组织在设计一个系统时，其产生的设计结构必然是该组织沟通结构的副本。"**

——这就是康威定律（Conway's Law）。

通俗地说：**如果你让四个团队分别负责前端、后端、数据库和运维，最终产出的系统一定是一个四层架构的系统，不管业务本身是否适合这样划分。** 因为系统的模块边界，天然会沿着团队的沟通边界形成。

在 Hermes Delivery 的早期，小陈团队只有 3 个人，大家坐在同一排桌子前，随时沟通——所以一个单体应用就足够了，沟通成本为零，没必要拆分。当团队扩张到 15 人且分成三个小组（订单组、调度组、支付组）后，如果代码仍然是单体，就会出现本章开头看到的困境——**团队边界已经形成，但系统边界没有跟上**。

### 2.5.2 逆康威定律

康威定律描述的是"组织结构决定系统架构"的客观现象。但有一个更有力的推论——**逆康威定律**（Inverse Conway Maneuver）：

> **如果你期望得到一个特定的系统架构，就先把团队组织成那个架构的样子。**

这是服务化设计中最实用的一条原则：**不是等架构设计好了再分配团队，而是先按你期望的服务边界来组织团队，让架构自然浮现**。

Hermes Delivery 的实践：

| 期望的服务架构 | 团队组织 |
|---------------|---------|
| 用户服务（独立部署） | 分配 2 人组成"用户服务小组"，对用户功能的全部生命周期负责 |
| 订单服务 + 支付服务 | "交易平台小组" 3 人，同时负责订单和支付的演进（这两个上下文联系紧密） |
| 配送调度服务 | "调度引擎小组" 4 人——这是核心域，投入最强力量 |
| 通知服务 | 1 人兼职维护 + 大量使用云服务商现成能力 |

### 2.5.3 康威定律对服务拆分的启示

康威定律及其逆命题给服务拆分提供了三条务实准则：

1. **不要让两个团队共享一个服务的代码所有权**。如果一个服务被两个团队同时修改，它就失去了自治性——这正是单体应用的困境。
2. **如果一个服务的变更总是需要另一个服务配合才能上线，考虑它们是否应该合并**。过度的拆分比适度的合并更有害。
3. **先调整组织结构，再调整服务边界**。当业务方向变化时，先 re-org，再 re-arch。

## 2.6 Hermes Delivery 建模实例

> 📊 **图2-2（见 `assets/ch02-ddd-process-flow.excalidraw`）**：DDD 战略设计五步流程图——从业务需求梳理→子域分类→限界上下文识别→微服务映射→上下文映射图产出，以 Hermes Delivery 为例展示了完整建模过程。将 `.excalidraw` 文件拖入 [excalidraw.com](https://excalidraw.com) 即可查看和编辑。

本节将前面所学的概念串联起来，完整演示如何对 Hermes Delivery 进行 DDD 战略建模。

### 2.6.1 从需求描述到领域划分

Hermes Delivery 的核心业务需求如下（精简版）：

```
Hermes Delivery 是一个同城/跨城快递配送平台。
1. 用户可以注册、登录、管理常用地址。
2. 用户下单时，选择取件地址、收件地址、包裹类型（文件/小件/大件），系统自动计算运费。
3. 支付成功后，系统根据骑手位置和订单信息自动派单。
4. 骑手接单后按规划路线取件、配送，用户可实时查看位置。
5. 配送完成后，用户可对骑手进行评价。
6. 系统支撑多条产品线（同城急送、跨城专送），每条产品线的计价规则和配送时效不同。
7. 运营后台可查看订单热力图、骑手分布、配送时效统计等报表。
```

### 2.6.2 子域分类

首先进行子域分析——区分核心域、支撑域和通用域：

```
Hermes Delivery 业务领域
│
├── 核心域 ──────────────────────────
│   ├── 智能调度子域
│   │   · 骑手-订单匹配算法
│   │   · 动态定价引擎（根据距离/天气/时段）
│   │   · 路线规划优化
│   └── 多产品线引擎（同城急送/跨城专送的差异化策略）
│
├── 支撑域 ──────────────────────────
│   ├── 订单管理子域（生命周期：待支付→已派单→配送中→已签收）
│   ├── 用户管理子域（注册/登录/地址簿）
│   ├── 评价子域（评分+文本评价+骑手等级）
│   └── 运营报表子域（热力图/时效统计/骑手绩效）
│
└── 通用域 ──────────────────────────
    ├── 支付子域（对接微信/支付宝）
    ├── 通知子域（短信/推送）
    └── 身份认证子域（JWT Token / OAuth）
```

**资源分配决策**：
- 调度子域投入 40% 的开发资源——这是 Hermes 区别于竞争对手的核心
- 通知和认证采用云服务商的现成方案，投入 <5% 的资源
- 支付对接微信和支付宝的 SDK，不重复造轮子

### 2.6.3 限界上下文识别与服务拆分

综合考虑子域分析和康威定律，形成最终的服务拆分方案：

| 限界上下文 | 对应服务 | 拆分依据 | 团队归属 |
|-----------|---------|---------|---------|
| 用户管理 | `user-service` | 支撑域 + 业务能力 | 用户平台组（2人） |
| 订单管理 | `order-service` | 支撑域 + 业务能力 | 交易平台组（3人） |
| 支付处理 | `payment-service` | 通用域（对接外部渠道） | 交易平台组（共用） |
| 智能调度 | `dispatch-service` | **核心域**，独立部署 | 调度引擎组（4人） |
| 计价引擎 | `pricing-service` | 核心域（动态定价），从调度中独立 | 调度引擎组（共用） |
| 用户评价 | `review-service` | 支撑域，低耦合可独立 | 用户平台组（共用） |
| 消息通知 | `notification-service` | 通用域（云服务） | 基础设施组（1人） |
| 运营报表 | `report-service` | 支撑域，数据密集型 | 数据平台组（2人） |

### 2.6.4 上下文映射图

```
                     ┌──────────────┐
                     │  用户服务     │
                     │  user-service │
                     └───┬────┬─────┘
              OHS/API    │    │  OHS/API
          ┌──────────────┘    └──────────────┐
          ▼                                  ▼
┌─────────────────┐                  ┌──────────────┐
│    订单服务       │   ACL(防腐层)     │   评价服务    │
│  order-service   │◄─────────────────│ review-service│
└────┬───────┬─────┘                  └──────────────┘
     │       │
     │       │ 事件驱动
     │       │ (发布语言: OrderPaid)
     │       ▼
     │  ┌─────────────────┐
     │  │    调度服务       │  ◄── 核心域
     │  │ dispatch-service │
     │  └────────┬────────┘
     │           │
     │           │ 事件驱动 (OrderDispatched)
     │           ▼
     │  ┌─────────────────┐      ┌─────────────────┐
     │  │   计价服务        │      │   通知服务        │
     │  │ pricing-service  │      │notification-svc  │
     │  └─────────────────┘      └─────────────────┘
     │                                   ▲
     │  OHS/API                          │ 事件订阅
     ▼                                   │
┌─────────────────┐              ┌──────┴──────────┐
│   支付服务        │              │   运营报表服务     │
│ payment-service  │              │  report-service  │
└─────────────────┘              └─────────────────┘
```

图中的关系模式：
- 用户与订单、评价之间是 **OHS（开放主机服务）** 关系——用户服务提供标准的用户信息查询 API，各服务通过 API 获取用户数据，而非直接读用户数据库。
- 订单与支付之间通过 **ACL（防腐层）** 隔离——支付服务对接微信/支付宝的外部模型，翻译为内部统一格式后交给订单服务。
- 调度与通知之间通过**事件驱动**——调度服务发布 `OrderDispatched` 事件，通知服务订阅并触发短信/推送。

### 2.6.5 关键架构决策记录

以下是在 Hermes Delivery 建模过程中做出的重要决策，以及决策理由：

| 决策 | 理由 |
|------|------|
| **计价引擎独立为 pricing-service，而非合并到 order-service** | 计价是核心域（动态定价），需要独立的迭代节奏和性能优化；订单是支撑域，变更频率不同。逆康威定律：已经为调度引擎组分配了最强团队，让其同时拥有调度和计价。 |
| **评价服务独立部署** | 评价是低耦合的支撑域，非常适合交给初级开发人员独立负责。独立部署后，评价服务的故障不影响下单和配送核心流程。 |
| **通知服务使用事件订阅模式，而非同步 API 调用** | 通知是"尽力而为"的辅助能力。如果订单服务同步等待短信发送成功，会导致不必要的延迟和耦合。事件驱动让通知服务可以异步消费，失败不影响主流程。 |

### 2.6.6 从上下文到代码：Go 项目结构示例

限界上下文不只是纸面上的概念——它们直接映射为代码的模块边界。以下是 Hermes Delivery 的 Go 项目仓库结构（monorepo 模式，每个上下文一个顶级目录）：

```go
// hermes-delivery/
// ├── cmd/                          # 各服务入口
// │   ├── user-service/main.go
// │   ├── order-service/main.go
// │   ├── dispatch-service/main.go
// │   ├── pricing-service/main.go
// │   ├── payment-service/main.go
// │   ├── review-service/main.go
// │   ├── notification-service/main.go
// │   └── report-service/main.go
// ├── internal/                     # 私有包，每个上下文一个子包
// │   ├── user/                     # 用户上下文
// │   │   ├── domain/               #   领域模型（实体、值对象）
// │   │   │   ├── user.go           #     User 聚合根
// │   │   │   └── address.go        #     Address 值对象
// │   │   ├── app/                  #   应用服务（用例编排）
// │   │   ├── infra/                #   基础设施（数据库、缓存）
// │   │   └── interface/            #   接口层（HTTP/gRPC handler）
// │   ├── order/
// │   │   └── domain/
// │   │       └── order.go          #   Order 聚合根
// │   ├── dispatch/                 #   核心域！
// │   │   ├── domain/
// │   │   │   ├── dispatch.go       #     Dispatch 聚合根
// │   │   │   └── matching.go       #     骑手匹配算法（核心逻辑）
// │   │   └── ...
// │   ├── pricing/
// │   ├── payment/
// │   ├── review/
// │   ├── notification/
// │   └── report/
// ├── pkg/                          # 可被多个上下文共享的公共库
// │   ├── events/                   #   领域事件定义（共享内核）
// │   │   ├── order_created.go      #     OrderCreated 事件
// │   │   └── order_dispatched.go   #     OrderDispatched 事件
// │   └── middleware/
// ├── api/                          # API 契约（OpenAPI / Proto）
// │   ├── user/v1/
// │   └── order/v1/
// ├── docker-compose.yml            # 本地一键启动
// └── go.mod
```

**关键设计决策体现在代码结构中：**

1. **每个上下文独占一个 `internal/` 子目录**——代码层面强制了边界，`order/` 不能直接 `import` `dispatch/` 的内部包，必须通过 `pkg/events/` 中的共享事件定义通信。
2. **`pkg/events/` 作为共享内核**——这是有限的、受控的共享：只共享事件的结构定义（字段名、类型），不共享业务逻辑。
3. **核心域 `dispatch/` 的目录结构更丰富**——包含 `matching.go`（骑手匹配算法）等核心逻辑文件，反映了"核心域值得最大投入"的原则。
4. **每个上下文内部采用 DDD 战术分层**（domain/app/infra/interface）——第 3 章将深入探讨内部分层设计。

## 2.7 常见误区

> ⚠️ 以下是在学习和实践中容易踩到的坑，提前认识它们可以避免走弯路。

### 误区一："一个限界上下文 = 一个微服务"

**错误认知**：识别出 N 个限界上下文，就应该创建 N 个微服务。

**纠正**：限界上下文是**逻辑边界**，微服务是**物理边界**。初期可以将多个密切协作的上下文部署在同一个服务中，随着业务演进再逐步拆开。Hermes Delivery 的订单和支付在初期可以共享一个服务进程，用模块（package）隔离上下文，等流量上来后再拆为独立服务。**过早拆分是微服务失败的首要原因**。

### 误区二："统一语言就是全公司统一术语"

**错误认知**：全公司都用同一套术语表，比如"用户"在所有系统里都叫 `User`。

**纠正**：统一语言是**上下文范围内**的统一。在配送上下文中，"用户"可能更适合叫"发件人（Sender）"和"收件人（Receiver）"，因为在配送场景中，这两个角色有不同的约束和操作。强行统一反而让模型失真。

### 误区三："核心域就是技术最难的部分"

**错误认知**：用了机器学习、用了 Kubernetes 的就是核心域。

**纠正**：核心域的定义是**业务差异化能力**，与技术复杂性无关。Hermes Delivery 的支付对接虽然涉及加密、签名、回调等复杂技术，但它仍然是通用域——因为每家快递公司接入支付的方式大同小异。相反，一条看似简单的"根据骑手位置和订单密度动态调整运费"的规则，可能才是核心域——因为它直接影响平台的营收和用户体验。

### 误区四："康威定律是一个问题，需要克服它"

**错误认知**：康威定律描述的是一个不好的现象，我们要想办法打破它。

**纠正**：康威定律不是问题，而是现实。与其对抗它，不如**利用逆康威定律主动设计组织**。让组织结构服务于你想要的架构，而不是被现有的组织边界束缚。

## 实验 2-A：用事件风暴工作坊划分上下文

> 本实验建议在课堂或小组讨论中完成，需 30-45 分钟。

### 实验目标

通过动手实践**事件风暴**（Event Storming）这一 DDD 核心工作坊方法，将一段业务需求转化为限界上下文和服务划分方案。

### 实验步骤

1. **准备材料**（5 分钟）：每组 3-5 人，准备便利贴（或白板 + 马克笔）。三种颜色的便利贴分别代表：
   - 🟠 橙色：**领域事件**（发生了什么？）
   - 🟡 黄色：**命令**（谁触发了什么？）
   - 🔵 蓝色：**聚合/实体**（事件涉及哪些核心数据？）

2. **事件风暴**（15 分钟）：阅读以下需求，按时间线贴出领域事件：

   > "用户在餐厅预订系统中搜索附近餐厅，选择餐厅后查看菜单并点餐。提交订单后，系统自动计算配送费并生成支付链接。用户支付成功后，订单发送到餐厅后台。餐厅接单并开始备餐。备餐完成后，系统分配骑手上门取餐。骑手取餐后，用户可实时查看配送位置。送达后用户确认收货并可评价。"

3. **上下文识别**（10 分钟）：将领域事件按业务相关性分组，每组成为一个候选的限界上下文，为每个上下文命名。

4. **展示与讨论**（10 分钟）：各组展示划分结果，全班讨论分歧点。重点关注：哪些事件的归属有争议？为什么？

### 实验产出

提交一份上下文映射草图（手绘或数字均可），包含：
- 上下文名称和核心职责（一句话）
- 上下文之间的主要数据流
- 至少一处标注上下文映射关系类型（如 OHS、ACL 等）
