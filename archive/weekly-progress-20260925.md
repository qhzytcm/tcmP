> 承接 9/22 技能记录的陷阱，本周巡检**首次以只读 `dispatch --dry-run` 取得直接证据**（纯只读，不 spawn、不写库）：

```
### tcm-epic        → Spawned: 0 | Skipped (unassigned): t_345e0b55, t_89000eac, t_80b16bd2,
                                                     t_2c70fc18, t_44cfcfec, t_07def166,
                                                     t_ff10c246, t_31d7a26c
```

- **结论（修正上周判断）**：看板零流转**不能只归因于 gateway 无进程**——`dispatch` 对无 assignee 的 ready 卡进入 `Skipped (unassigned)` 分支，**不会自动指派给任何 profile**。因此**即便 gateway 恢复，这 34 张卡仍不会被领取**。
- **当前死锁链的准确表述**：`无 assignee（34 卡）→ dispatch 跳过 → 无 worker → 0 流转 → 0 产出`；gateway 无进程是**并列的第二重阻塞**，而非唯一根因。
- ⚠️ 补 assignee（`hermes kanban assign <id> <profile>`）会**真实拉起多智能体 worker**（成本/副作用显著），须先与项目方确认对象后再执行——巡检任务不代做。
